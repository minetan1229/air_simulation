## [Origami Geometry] (2026-10-20)
- 正本実装は `physics/origami_domain.py`（純幾何、飛行力学に非依存）。展開図→三次元ヒンジ列→多層ソリッド生成までを一括で持つ。
- **用紙は正方形でない**ため、(u,v) 平面の法線は三次元で折り目に直交しない。折り目は実寸の紙面（210×297 mm）で定義し、side normal は紙面内で三次元直交Directions として再構築する（flat そのまま使うと折れ目の向きが 45°ずれる）。
- 折り目は**現在位置**を軸に回す（`T' = F ∘ T`）。flat 定義のまま回すと、folded 済み層で crease がずれ、層が千切れる。折り目定義は「その折り目が実際に切る面」を単位とする group スコープで分離する（スコープ無しだと先に折った flap を後続 crease が貫通する）。
- **Z-Fighting 排除**: 面インデックスは「平行かつ投影重なり」クラスタの最長路（重なりDAG）で決める。重なった任意2面は ≥1 レイヤーピッチ（0.42 mm）離れるので、紙厚 0.30 mm に対して構造的に共面になり得ない。オフセットは α に比例（α=0 は平たい紙）。折れ目は 3 次ベジエのロール（両パネルに接線連続）で閉じ、境界が skin と roll で完全に一致する。flat 面法線をそのまま使うと法線が不連続になる。A4 斜辺は 45° ではない（1:√2 のため）。45° 相当は**紙面（三次元）での角度**で定義する。テストは `tests/test_origami.py`（39件）、Z-Fighting 判定は「重なった面の中間面距離 + 層差×ピッチ > 紙厚」。残課題の正本は `no-finish.md`（A-13〜A-19 据え置きと D §4.5 の G-1〜G-8 繰延）。 **2026-10-22 追記（crease 交点の特異点 = 台帳 §7.1 P0-4）**: 2 パネルがほぼ平行になると交点 `v` が不定距離に飛び（機首前方に 302 mm のスパイク）、旧退化判定 `denom <= 1e-20` は実失敗角 1e-8 rad に対して 2 桁甘かった。**幾何学境界での判定**へ変更（`physics/origami_domain.py:91` `CREASE_DEGENERATE_ANGLE_RAD = 1.0e-3` / `:98` `CREASE_DEGENERATE_DENOM = 1.0e-6` / `:1137-1141` で `denom <= CREASE_DEGENERATE_DENOM` なら有限値へ退避）。回帰固定化 `tests/test_origami.py:449` `test_bezier_crease_no_spike_across_parameter_sweep`、コミット `7639895`。

- ① **kilo CLI の実体パスは版数依存**（VS Code 拡張の自動更新で `kilocode.kilo-code-<ver>-win32-x64/bin/kilo.exe` の版数 dir が変わる。ハードコード禁止。path が古くなると `kilo run` は**出力ゼロ・exit 0**で即終了し「完了」と誤判定される）。② **中断された試行の `kilo.exe` 子が孤児として生存**（各 ≒550 MB、20 本で 98 % メモリ）。親ラッパが死んだ `kilo.exe` は**回収**する（実測 20 本 ≒12.6 GB → 98.3 % → 58.3 %）。③ レポートは**インクリメンタルに書き**、完了マーカーは完成後にだけ書く。④ **台帳の同期は「解消済み（コミット: <hash>）」の形で行い、台帳行は削除しない**（`no-finish.md` §10 の運用ルール）。判定は必ず **file:line + 再現コマンド + 実行したテスト結果**の 3 点で裏取りし、**`git log -S` / `git blame` で該当コミットを特定**する（作業ツリーの未コミット差分ではなく**コミット単位**で確かめる）。**`AGENTS.md` §1.2 により偶然動作での完了認定は禁止**。⑤ **台帳の `file:line` は「監査時点のツリー」の行番号**である。削除済みコードの行番号は現行ツリーで**再現しない**ので、削除前後の双方を明示するには `git show <commit>:<path>` で該当ツリーを取り出して行番号を実測する（実例: `torque_rate[1] *= 0.10` は `:1498`=`9538f8b` / `:1512`=`7639895`・`d287af2` / `:1517`=`8a41586` の各ツリーに実在し、`c4b9286` で消滅）。**台帳内部の相互参照**（§7.0 対照表の行番号など）も新行番号へ追従させ、**参照先のコードが現存しない行番号は断定に使わない**。 ⑥ **台帳は「正本」と「スナップショット」が二重に存在する**: `no-finish.md` §0.1 が**正本**（完了状況チェックリスト）、§7.x の「判定」欄は**採取時点のスナップショット**（§10 の運用ルール）。**両者が矛盾したら、どちらかを相信せずコード・テスト・`git log -S` で再判定する**（W13 では §0.1「P0 すべて完了」と §7.1 の「構造未変（要再計測）」「検証済（残存）」「要再検証」が矛盾 → P0-4〜P0-9 を再判定して解消済みと確定）。**ヘッダ 1 行の書き換えでも以降行番号がずれるため、台帳内部の相互参照は行番号を最後に一括再採番**する（W13 で `:217`→`:218` 等が発生）。**UI 系は「静的一致合」で裏取る**: JS の `getElementById` / `querySelector('#…')` / `$('#…')` が参照する id と `templates/*.html` の `id=` 宣言の**差分を数える**（未宣言 0 件＝死んだ id なし）。
